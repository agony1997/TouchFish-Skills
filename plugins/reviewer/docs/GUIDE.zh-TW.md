# reviewer 技能使用指南

> 版本：1.2.0 | 最後更新：2026-03-02

## 這是什麼？

專案規範審查與萃取工具 — 讀取你專案中的規範文件（如 `.standards/` 目錄），對程式碼進行合規審查；或從現有程式碼反向萃取隱含慣例，自動產出規範草稿。

**核心概念**：Skill = 審查 + 萃取工作流。規範內容由你維護在專案 repo 中，skill 本身不包含任何規範內容。

## 重要概念

| 概念 | 說明 |
|------|------|
| 規範文件 | 由你維護在專案中的 `.standards/` 目錄（或其他路徑） |
| 審查工作流 | 4 步驟流程：定位 → 確認範圍 → 執行 → 產出報告 |
| 萃取工作流 | 4 步驟流程：偵察 → 並行分析 → 合併 → 產出草稿 |
| Progressive Disclosure | 只載入需要的規範檔案，減少 context 佔用 |

## 意圖偵測

Skill 會根據你的指令自動判斷要執行哪個工作流：

- **審查關鍵字**（review、審查、檢查、compliance）→ 審查工作流
- **萃取關鍵字**（extract、萃取、generate standards、產出規範、慣例分析）→ 萃取工作流
- **模糊指令** → 會詢問你要審查還是萃取

## 審查工作流

```
觸發審查
   │
   ▼
┌─────────────────────────┐
│ Step 1: 定位規範文件     │
│ .standards/ → CLAUDE.md │
│ → 詢問使用者             │
│ → 或啟動萃取工作流       │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Step 2: 確認審查範圍     │
│ 哪些檔案？審查深度？     │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Step 3: 執行審查         │
│ 逐項核對已載入的規範     │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Step 4: 產出審查報告     │
│ Markdown 表格 + 統計     │
└─────────────────────────┘
```

### 步驟 1：定位規範文件

觸發後，skill 會按順序尋找規範：

1. **慣例路徑**：`.standards/`、`docs/standards/`、`standards/`
2. **CLAUDE.md 指示**：檢查專案 CLAUDE.md 是否指定規範路徑
3. **詢問使用者**：以上都找不到時，提供三個選項：
   - 手動指定規範文件路徑
   - **啟動萃取工作流**，從現有程式碼自動產出規範草稿
   - 手動建立 `.standards/` 目錄（參見下方「專案端設置指南」）

若專案尚無規範文件，建議先執行萃取工作流。

### 步驟 2：確認審查範圍

Skill 會詢問：

- **要審查哪些檔案？** — 指定檔案 / 最近修改的檔案 / 整個功能模組
- **審查深度？** — 快速掃描 / 完整審查

### 步驟 3：執行審查

以載入的規範文件內容為準逐項核對，通用審查維度包含：

- 命名規範（類別、方法、變數、檔案路徑、常數）
- 架構規範（架構模式、層級職責、相依方向）
- 程式碼風格（工具類別、錯誤處理、API 格式、日誌）
- 資料庫規範（Entity 對應、Migration 命名、索引）
- 前端規範（元件結構、狀態管理、型別定義）

### 步驟 4：產出審查報告

產出 Markdown 格式報告，包含：

- 專案資訊與載入的規範清單
- 不合規項目表格（檔案、行號、規範項目、問題描述、建議修正）
- 合規項目摘要
- 統計總結（審查數、合規數、不合規數、合規率）

## 萃取工作流

從現有程式碼反向萃取隱含的編碼慣例，自動產出 `.standards/` 草稿檔案。

```
觸發萃取
   │
   ▼
┌─────────────────────────────┐
│ E1: 偵察                     │
│ 偵測技術棧 + 判斷適用維度    │
│ 確認範圍與已知慣例           │
└───────────┬─────────────────┘
            ▼
┌─────────────────────────────┐
│ E2: 並行維度分析             │
│ 按維度分派 sub-agents        │
│ 各自取樣分析                 │
└───────────┬─────────────────┘
            ▼
┌─────────────────────────────┐
│ E3: 合併與評分               │
│ 合併報告、標記信心度         │
│ 確認取捨                     │
└───────────┬─────────────────┘
            ▼
┌─────────────────────────────┐
│ E4: 產出 .standards/ 草稿   │
│ 逐檔確認後寫入               │
│ 建議跑審查驗證               │
└─────────────────────────────┘
```

### E1：偵察

- 若專案有 `PROJECT_MAP.md`（explorer 產出），直接讀取技術棧和專案類型
- 否則快速掃描根目錄的 build 與 config 檔案判斷技術棧
- 判斷適用維度：
  - **必定分析**：naming、architecture、code-style
  - **有資料庫 artifacts 時**：database
  - **有前端 artifacts 時**：frontend
- 確認要分析的維度、範圍、已知慣例

### E2：並行維度分析

- 每個維度分派一個 sub-agent 並行分析
- 每個 sub-agent 最多取樣 30 個檔案，優先取樣多樣性
- **小專案旁路**（<10 個原始碼檔案）：跳過 sub-agents，直接分析

### E3：合併與評分

- 合併各維度報告，每條慣例評分：
  - **High**（>80% 檔案一致）→ 進草稿
  - **Medium**（50-80%）→ 進草稿
  - **Low**（<50%）→ 附錄「可能的慣例」
- 標記矛盾（專案本身的不一致，非誤判）
- 呈現摘要供你取捨

### E4：產出草稿

- 按維度產出 `.standards/{dimension}.md` 草稿檔
- 每個檔案逐一確認後才寫入
- 所有產出標記為 **DRAFT**，需人工審閱後才正式採用
- 建議產出後執行審查工作流驗證

## 專案端設置指南

在專案中建立規範文件目錄：

```
your-project/
├── .standards/
│   ├── common.md          # 公司/團隊共通規範
│   └── project.md         # 本專案特有規範
├── src/
└── ...
```

多份規範檔案會全部載入，可自由組織（依公司/團隊/專案拆分）。

規範檔案建議包含的章節（按需取捨）：

- 命名規範（類別、方法、變數、檔案路徑、常數）
- 架構規範（架構模式、層級職責、相依方向）
- 程式碼風格（工具類別、錯誤處理、API 格式、日誌）
- 資料庫規範（Entity 對應、Migration 命名、索引）
- 前端規範（元件結構、狀態管理、型別定義）

> 沒有規範文件？說「extract standards」或「萃取規範」，讓 skill 自動從程式碼萃取草稿。

## 常見問題

**Q: 規範文件放哪裡？**
A: 建議放在專案根目錄的 `.standards/` 資料夾。也支援 `docs/standards/` 和 `standards/`。

**Q: 可以有多份規範文件嗎？**
A: 可以，所有找到的規範文件都會載入。建議依公司/團隊/專案拆分。

**Q: Skill 會自動修正不合規的程式碼嗎？**
A: 審查報告產出後會詢問是否修正。Minor/Major 直接修正，Critical 會先確認修正計畫。

**Q: 沒有規範文件怎麼辦？**
A: 可以使用萃取工作流！說「extract standards」或「萃取規範」，skill 會從現有程式碼自動分析並產出 `.standards/` 草稿檔。草稿標記為 DRAFT，需人工審閱後才正式採用。

**Q: 萃取出來的規範準確嗎？**
A: 萃取結果基於對現有程式碼的統計分析，每條慣例附帶信心度（High/Medium/Low）和至少 3 個證據檔案。Low 信心度的項目會放入附錄供參考。最終需要你審閱確認，因此所有產出都標記為 DRAFT。

**Q: 萃取和審查可以搭配使用嗎？**
A: 這是推薦做法！先用萃取工作流產出規範草稿，審閱確認後，再用審查工作流驗證程式碼合規性。
